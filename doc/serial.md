# Протокол обмена CA51F2 <-> ZT3L (UART, 8N1, 115200)

## Структура пакета

| Header | SEQ | Flags | Status | Cmd ID | DLC | Type | Payload | CRC |
|--------|-----|-------|--------|--------|-----|------|---------|-----|
| 2 bytes | 1 byte | 1 byte | 1 byte | 1 byte | 1 byte | 1 byte | 0–64 bytes | 1 byte |

Максимальная длина кадра: 2+1+1+1+1+1+1+64+1 = **73 байта** (влезает в буфер
приёмника 8051, XDATA). Минимальная (нет полезных данных, `DLC=0`) — **8 байт**:
заголовок, SEQ, Flags, Status, Cmd, DLC, CRC (Type и Payload отсутствуют).

## Fields

| Field | Value | Description |
|-------|-------|-------------|
| Header | `0xAA` `0x55` | Определение начала пакета. Порядок байтов — не косметика: при смешанных прошивках сторона со старым заголовком вообще не синхронизируется, поэтому гонка «новый ZT3L + старый CA51F2» (или наоборот) отсекается ещё на поиске заголовка, а не на CRC. При ошибке CRC приёмник ищет следующий `AA 55` (ресинхронизация). |
| SEQ | 0–255 | **Счётчик у каждой стороны свой**: своя сторона увеличивает его на 1 перед **любой собственной** отправкой (запрос, команда, данные/репорт). **Ответ копирует SEQ запроса** (чужого счётчика) и свой счётчик не трогает. Дедупликация — по паре (Cmd ID, SEQ). |
| Flags | биты 0–2: `RSP` / `ACK` / `CMD`; 3–7 = 0 | См. ниже. Зарезервированные биты (3–7) слать как 0; **при приёме не игнорируются, а отвергаются** (`0x13 BAD_FLAGS`) — централизованная валидация. |
| Status | `0x00` = OK, `!= 0` = ошибка | **Только у ответов** (классы и полный список — в разделе «Ошибки (Status)»). У всех остальных кадров = 0. |
| Cmd ID | 0–255:<br>`0x00–0xBF` — данные/команды<br>`0xC0–0xDF` — ОТА<br>`0xE0–0xFF` — резерв | Диапазоны зарезервированы заранее. В `0x00–0xBF` — время, температура, заданная температура, режим, расписание по дням, ping/версия прошивки, заводской сброс и т.п.; ОТА выделена отдельно (подсистема, добавляемая позже, чтобы не занять её ID раньше времени); резерв — см. примечание ниже. |
| DLC | 0–64 | Длина **Payload** (только данных, не Type). Если `DLC=0` — полей Type и Payload **нет**, сразу после DLC идёт CRC. |
| Type | `0`=bool<br>`1`=enum(u8)<br>`2`=u8<br>`3`=i8<br>`4`=u16<br>`5`=i16<br>`6`=u32<br>`7`=i32<br>`8`=float(32)<br>`9`=резерв<br>`10`=string (UTF-8/ASCII, без терминатора)<br>`11`=RAW (внутренний формат задаётся Cmd ID)<br>`12`=bitmap8 (1 байт)<br>`13`=bitmap16 (2 байта BE)<br> | Присутствует **только если `DLC>0`**. Многобайтные числа — **big-endian** (как формат времени ZT3L: `utc`+`local` по два u32 BE). |
| Payload | 0–64 байт | **OTA-блоки по кадру НЕ ходят**: после `0xC0` обе стороны переключаются в сырой режим, где блок = `SYNC/OFF(2)/LEN/DATA(1..128)/CRC8` (см. «OTA CA51F2 через Zigbee»). |
| CRC | CRC-8/MAXIM: poly `0x31`, init `0x00`, отражающая, xorout `0x00` | По всем байтам **от Header до Payload включительно** (без самого CRC). |

## Flags

| Bit | Name | Meaning |
|-----|------|---------|
| 0 | RSP | `1` = это **ответ** на запрос/команду (SEQ скопирован из запроса); `0` = инициатива. |
| 1 | ACK | `1` = инициатор **ждёт ответ**; `0` = не ждёт (репорт/данные). Для ответов ACK всегда `0`. |
| 2 | CMD | `1` = это **команда** (действие: установить, включить, сбросить и т.п.); `0` = это данные (значение/состояние, даже если идёт как репорт). |
| 3–7 | — | Резерв = 0. |

Недопустимы: `RSP=1 && ACK=1`; `CMD=1 && ACK=0` (команда без ожидания
подтверждения не предусмотрена). **Обе комбинации отвергаются приёмником**
(`LNK_ST_BAD_FLAGS`), как и любой установленный бит 3–7.

Проверка выполняется **до диспетчеризации** и до любых побочных эффектов:

1. **Flags** — зарезервированные биты, `RSP|ACK`, `CMD` без `ACK` → `BAD_FLAGS`.
2. **DLC** — `DLC > 64` → `BAD_LEN` (предел кадра, не схема).
3. **Роль** — запрошенная роль (Report / Req / Cmd) должна входить в маску ролей
   команды, иначе `BAD_FLAGS` (на ZT3L роль закодирована точными Flags в
   shape-таблице, отдельного шага нет).
4. **Длина и Type** — затем длина сверяется со схемой команды → `BAD_LEN`;
   при `DLC > 0` тип обязан совпадать со схемой → `BAD_TYPE`.
5. **Рукопожатие** — мутационные settings/system-команды до Info не принимаются
   (`0x32 NOT_READY`). Набор «разрешено до Info» у сторон свой:
   CA51F2 — Info, Net status, `0xC0 OTA_START`, `0x2B` ALIVE; ZT3L — Info,
   температуры `0x02`/`0x03`, Net status, `0x2A` boot, `0xC0 OTA_START`, плюс
   TIME/расписание только с `flags == ACK`. Read-only TIME/schedule-**запросов**
   у CA51F2 больше нет (роль Req удалена как мёртвый путь: TIME и SCHED —
   чужой Req получает `BAD_FLAGS`).
6. **Диапазон/состояние** — только после успешных 1–5 (см. «Ошибки (Status)»).

Схемы реализованы раздельно: `lnk_validate()` на CA51F2 (`src/link_proto.c`) и
`app_link_validate()` в `App_Link_OnFrame()` на TLSR8258 (`src/app_link.c`);
шаги 1–4 идентичны по смыслу, шаг 5 отличается (см. выше). Неизвестная команда с `ACK` → `0x10 UNSUPPORT`; неизвестный
`RSP` с `DLC=0` допускается (через него проходят ответы на `0x09`, температуры
и factory reset, которые CA51F2 сам как входные команды не принимает).

Семантика кадров:

| Кадр | Flags |
|------|-------|
| Запрос данных («дай значение X») | RSP=0, ACK=1, CMD=0 |
| Команда («выполни действие X», ждёт OK/Error) | RSP=0, ACK=1, CMD=1 |
| Отчёт/данные (самостоятельная отправка) | RSP=0, ACK=0, CMD=0 |
| Ответ (на запрос или команду; содержит Status и, при запросе, данные) | RSP=1, ACK=0, CMD=0 |

Таймаут/ретрай: если ACK=1, инициатор ждёт ответ; при таймауте 100 мс повторяет
тот же SEQ ещё 2 раза (итого 3 попытки), затем цикл раз в 30 с (подробнее —
раздел «Ретраи запросов»).

Резерв (`0xE0–0xFF`): запас на будущие подсистемы (например, диагностика/дли
событий, смена формата и пр.), которые появятся **после** ОТА. Он не обязателен,
но стоит дёшево: 32 ID из 256 — 12% — и защищает от переименования уже
развёрнутых команд, когда какая-то новая подсистема «внезапно» понадобится с
самыми высокими ID.

## Приёмный тракт (буфер и ресинхронизация)

Общие правила на обеих сторонах (CA51F2 `src/uart.c`, TLSR `src/app_uart.c`) —
первые три пункта; пункт про TX действует только на CA51F2:

- **Один зарезервированный слот.** Кольцо приёма держит `N-1` полезных слотов;
  при переполнении ISR **не перезаписывает** данные, а увеличивает
  насыщаемый (`volatile uint16_t`, saturating) счётчик **epoch** и теряет байт.
- **Обнаружение переполнения — в main-контексте.** `Uart1_Poll()` /
  `App_Uart_Poll()` снимают эпоху **до** чтения кольца и **непосредственно перед**
  передачей байта в разборщик; при изменении эпохи FSM приёма сбрасывается в
  режим поиска заголовка `AA 55` **до** первого байта. Гонки с ISR нет: сброс
  выполняется только в main.
- **Терминирующий байт возвращается в распознаватель.** При плохом CRC или
  слишком большом DLC последний байт кадра прогоняется через sync-распознаватель
  заново, поэтому `AA 55` ровно на этой границе не теряется.
- **Формирование кадра TX целиком (только CA51F2).** Кадр сначала целиком
  ставится в кольцо отправки (ISR выдаёт байты подряд), и только потом
  логируется. У ZT3L кольца TX нет (DMA `drv_uart_tx_start`), и лог `TLSR ->`
  пишется **до** вызова драйвера. Побочный эффект на CA51F2: между кадрами
  в логе остаются паузы; для чистого захвата на осциллографе отключить `LINK_EN`.

## Ошибки (Status)

`Status` заполняется **только в ответах** (`RSP=1`): `0x00` — выполнено/данные,
`!= 0` — ошибка (Payload пустой). Исходящие репорты и команды несут Status `0`;
ответа нет **только у репортов** (`ACK=0`), команда (`ACK|CMD`) всегда получает
ответ. Битый CRC — кадр молча дропается (ресинк по `AA 55`),
ответить нечем.

Порядок проверки: Flags → DLC → Type → поддержка сущности → диапазон →
состояние. Старший ниббл кода — класс:

| Код | Имя | Смысл |
|-----|-----|-------|
| `0x00` | OK | выполнено / данные |
| **0x1x** | кадр/протокол | |
| `0x10` | UNSUPPORT | неизвестный Cmd ID / сущности нет на этой плате |
| `0x11` | BAD_LEN | неверная DLC для сущности |
| `0x12` | BAD_TYPE | неверный Type для сущности |
| `0x13` | BAD_FLAGS | недопустимая комбинация Flags |
| `0x15` | BAD_VER | несовместимая версия протокола (Info) |
| **0x2x** | значение | |
| `0x20` | RANGE | значение вне диапазона |
| `0x21` | VALUE | недопустимое значение (enum) |
| `0x22` | READONLY | сущность только для чтения |
| **0x3x** | состояние | |
| `0x30` | NO_DATA | значения пока нет |
| `0x31` | BUSY | занято (например, OTA) |
| `0x32` | NOT_READY | рукопожатие/инициализация не завершены |
| `0x33` | NOT_PERMITTED | запрещено (блокировка клавиш) |
| `0x34` | MODE | операция недопустима в текущем режиме |
| **0x4x** | внутреннее | |
| `0x40` | INTERNAL | внутренняя ошибка |
| `0x41` | FLASH | ошибка записи в flash |
| `0x42` | CORRUPT | повреждённый образ настроек |

Реакция отправителя: `0x1x` — не повторять (`UNSUPPORT` → пометить сущность как
неподдерживаемую); `0x2x` — не повторять, вернуть наверх; `0x3x` — `NO_DATA`/
`BUSY`/`NOT_READY` можно повторить позже, `NOT_PERMITTED`/`MODE` — наверх; `0x4x`
— не повторять, лог/наверх. Значения вне диапазона **отклоняются** (не
зажимаются). Коды — `LNK_ST_*` в `link_proto.h`.

**Повторный SEQ (дедупликация).** Инициатор повторяет
запрос с тем же SEQ. Чтобы повтор уже выполненной команды не исполнился дважды,
приёмник хранит **один** слот «последний (Cmd, SEQ) + готовый ответ»
(status / type / len / payload до 24 Б) и на совпадение пары пересылает cached
ответ, **не исполняя** обработчик заново. Новая пара `(Cmd, SEQ)` замещает слот.

- Покрывает Info, factory reset (`0x27`), boot notice (`0x2A`), настройки
  (`0x07/0x0B/0x0C/0x0D/0x0E/0x0F/0x10/0x11/0x17/0x1A/0x1B`), время (`0x00`),
  System Mode (`0x0A`) и расписание (`0x20..0x26`) — на обеих сторонах.
- Cached payload лежит в **отдельном** буфере (`link_dedup_payload[]`), поэтому
  поздняя переиспользование scratch-буфера отправки не подменяет ответ.
- **Отчёт без ACK** (`Flags == 0`, напр. спонтанный Net-status с ZT3L; текущая
  CA шлёт температуры `0x02/0x03` уже **с ACK**) дедуп-слот **инвалидирует**
  и ответа не порождает — иначе такой отчёт нельзя было бы отличить от
  повторной команды.
- **Новая сессия** (новый Info с новым SEQ) очищает дедуп-слот, peer-состояние,
  очередь надёжных сообщений, дамп состояния и ретраи boot/factory, и
  увеличивает `link_session`. Тот же Info-SEQ обрабатывается дедупом и сессию
  **не** сбрасывает. Слот очереди хранит `session` и проверяется в poll/приёме
  ответа, поэтому поздний RSP старой сессии не освобождает новый слот.
- Слот очереди, уже вошедший в `WAIT_RSP`, при замене payload получает **новый
  SEQ**; поздний RSP старой пары `(SEQ, Cmd)` не освобождает замену.

## Старт и рукопожатие (Cmd `0x01` Info, `0x1F` Net status)

Инициатор старта — **ZT3L (TLSR8258)**. Если же перезагружается CA51F2, он сам
уведомляет об этом (Cmd `0x2A`, см. «Уведомление о рестарте CA51F2»), и ZT3L
сразу запускает рукопожатие с шага 2. Последовательность (старт по питанию):

| # | Момент | Отправитель | Кадр | Flags | DLC | Type |
|---|--------|-------------|------|-------|-----|------|
| 1 | t = 0 | — | подача питания | — | — | — |
| 2 | t = 1.0 с | ZT3L | **Info Req** (`0x01`) | `0x02` (ACK) | 0 | — |
| 3 | сразу | CA51F2 | **Info Rsp** (`0x01`) | `0x01` (RSP) | 5..21 | `11` RAW |
| 4 | +100 мс после шага 3 | CA51F2 | **Net status Req** (`0x1F`) | `0x02` (ACK) | 0 | — |
| 5 | сразу | ZT3L | **Net status Rsp** (`0x1F`) | `0x01` (RSP) | 1 | `1` enum |
| 6 | после шага 5 | ZT3L | **State-all Req** (`0x28`) | `0x06` (ACK\|CMD) | 0 | — |
| 7 | сразу | CA51F2 | **State-all Rsp** (`0x28`) | `0x01` (RSP) | 0 | — |
| 8 | после шага 7 | CA51F2 | **дамп настроек** — по одному кадру, следующий после ответа | `0x06` (ACK\|CMD) | — | — |

- **Шаг 1.** Подача питания (`t = 0`): CA51F2 поднимает UART1 сразу и далее
  выполняет ~5-секундный boot-тест (входящие запросы обслуживает уже в нём),
  ZT3L отсчитывает свою паузу 1 с перед шагом 2.
- **Шаг 2.** ZT3L ждёт **1 с** после подачи питания
  (`LINK_BOOT_DELAY_TICKS` в `app_link.c` — CA51F2 отвечает на запросы уже во время своего boot-теста),
  затем шлёт запрос Info. Ответ (шаг 3) копирует SEQ запроса.
- **Шаг 3.** CA51F2 отвечает своей идентичностью, взводит `Link_PeerAlive()` и
  запускает таймер на **100 мс**.
- **Шаг 4.** По таймеру CA51F2 сама (свой SEQ) шлёт запрос статуса сети.
- **Шаг 5.** ZT3L отвечает статусом (`LNK_NET_FREE` / `LNK_NET_CONNECTED` /
  `LNK_NET_ERROR`), SEQ копируется из запроса.
- **Шаг 6.** ZT3L шлёт `State-all Req` (`0x28`, `ACK|CMD`, DLC 0).
- **Шаг 7.** CA51F2 отвечает OK.
- **Шаг 8.** CA51F2 выгружает конфигурацию по одному кадру — следующий только
  после ответа на предыдущий (см. «Дамп настроек»).
- После шага 3 ZT3L сам инициирует ровно три вещи: дамп `STATE_ALL` (шаг 6),
  спонтанный репорт статуса сети при его изменении (см. ниже) и alive-пинг
  `0x2B` раз в 60 с (см. «Действия»); остальное время только отвечает.

Payload Info (RAW, **5..21 Б**, схема из `include_common/link_proto.h`):

| off | Поле | Тип | Пример |
|-----|------|-----|--------|
| 0 | `ver_proto` | u8 | `0x01` — текущая схема кадра |
| 1 | `ver_app` | u16 BE | BCD-версия прошивки: старший байт — мажор, младший — минор (`0x0100` = v1.00) |
| 3 | `chipid` | u16 BE | код чипа: `0x20A0` = CA51F253L3 (из скрытой области 0x2B, см. `tools/cachip-isp-serial_new.py`) |
| 5 | `model` | string | ≤`LNK_INFO_MODEL_MAX` = **16** Б ASCII без терминатора: `osrctherm_r02` / `ZR_Therm` |

Длина Info — **переменная** (`LNK_INFO_MODEL .. LNK_INFO_MAX_LEN`, т.е. 5..21) и
несёт ровно столько байт model-строки, сколько реально нужно. Проверка приёма
(`lnk_validate`): `DLC < 5 || DLC > 21` → `BAD_LEN`; `Type != RAW` → `BAD_TYPE`;
эталонная длина `5` (модель пустая) тоже допустима. ZT3L проверяет Info
**ответ** на версию CA51F2 только при `Status = OK` **и** полной длине
version-поля — иначе OTA-передача не стартует (см. «OTA CA51F2 через Zigbee»).
Парсер ZT3L копирует строку в буфер с нулём-терминатором; из-за
переменной длины значения 6..21 Б на ZT3L раньше разбирались иначе, чем
выдавал CA51F2 — теперь приёмник сверяет диапазон, а не фиксированный размер.

ZT3L, получив Info, по `chipid` знает, какой чип перед ним, а по `model` — какой
вариант прошивки.

**Коды:** `LNK_CMD_INFO = 0x01`, `LNK_CMD_NET_STATUS = 0x1F`,
`LNK_PROTO_VER = 0x01` (определены в `link_proto.h`).

**Ретраи запросов.** Если ответ не пришёл за **100 мс**, инициатор повторяет тот
же SEQ ещё **2 раза** (итого 3 попытки с интервалом 100 мс). Если снова нет
ответа — пауза **30 с**, и цикл из 3 запросов повторяется. Так по кругу, пока
ответ не придёт (после первого ответа повторов больше нет). Это правило
одинаково для Info-запроса ZT3L и Net-status-запроса CA51F2.

**Уведомление о рестарте CA51F2 (Cmd `0x2A` CA51F2_BOOT).** ZT3L не видит сброс
CA51F2, поэтому после нормальной загрузки (после ~5 с boot-теста) CA51F2 сам шлёт
`LNK_CMD_CA51F2_BOOT` (`0x2A`, Flags `0x06` ACK\|CMD, DLC 0). ZT3L отвечает OK
(SEQ копируется) и **сразу** запускает новое рукопожатие: шлёт Info Req (шаг 2),
сбросив своё состояние CA51F2 (`link_ca51f2_alive`, флаги рукопожатия, очередь
надёжных сообщений) и форсировав репорт статуса сети. Если OK не пришёл за **3 с**,
CA51F2 повторяет `0x2A` (тот же SEQ) — и так **бесконечно**, пока не получит OK.
После OK повторов нет. Это дополняет инициативу ZT3L: оба пути сходятся на шаге 2.

**Статус сети после старта.** После успешного обмена (шаг 5) CA51F2 больше
статус не перезапрашивает. ZT3L сам шлёт **репорт** статуса сети (`0x1F`,
Flags `0x00`: RSP=0, ACK=0, CMD=0, Type `1` enum, 1 Б `LNK_NET_*`) только при
**изменении** статуса (например, прибор вышел из сети). CA51F2 применяет
репорт без ответа (иконка сети).

**Дамп настроек (шаги 6–8).** После ответа по статусу сети ZT3L шлёт
`LNK_CMD_STATE_ALL` (`0x28`, `ACK|CMD`); CA51F2 отвечает OK и затем шлёт
конфигурацию **по одному кадру**, каждый — **команда** (`ACK|CMD`): следующий
шлётся только после ответа пира; нет ответа 100 мс → повтор тем же SEQ, 3
попытки, далее раз в 30 с. **Температуры в дамп не входят** — они идут отдельно
(`0x02`/`0x03`: первый раз после рукопожатия, далее по политике изменения/keepalive, см. ниже).
Порядок:

| # | Cmd | Значение |
|---|-----|----------|
| 1 | `0x0C` | `sensosUsed` |
| 2 | `0x0D` | `localTemperatureCalibration` |
| 3 | `0x0E` | `outTemperatureCalibration` |
| 4 | `0x0F` | `deadBand` |
| 5 | `0x0B` | `progMode` |
| 6 | `0x10` | `minHeatSetpointLimit` |
| 7 | `0x11` | `maxHeatSetpointLimit` |
| 8 | `0x07` | `occupiedHeatingSetpoint` |
| 9 | `0x17` | `keypadLockout` |
| 10 | `0x1A` | `currentLevel_day` |
| 11 | `0x1B` | `currentLevel_night` |
| 12 | `0x0A` | `systemMode` |
| 13 | `0x09` | `runningState` (текущий бит реле) |
| 14–20 | `0x20`..`0x26` | расписание, по дню (24 Б) |

Всего **13 скалярных** кадров (включая `0x09`) + 7 дней = **20 кадров**. Следующий
кадр отправляется только после `RSP OK`; при `RSP` с ошибкой тот же SEQ
повторяется (пауза/цикл — по классу status), дамп **не** продвигается.
**Лимит на постоянную ошибку:** классы `0x3x`/`0x4x`
(временные: `NOT_READY`, `BUSY`…) ретраятся быстро и вечно — они
самоизлечиваются; любая **постоянная** ошибка (`UNSUPPORT`, `RANGE`,
`BAD_TYPE`…) после `LNK_DUMP_PERM_MAX = 3` повторов **снимает дамп**
(`link_dump_active = 0`) — иначе один отвергнутый кадр повторялся бы раз в
30 с вечно, а остальные 19 кадров не ушли бы никогда (рассинхрон версий,
которым дамп не починить). Счётчик чистится при старте дампа и на каждом
принятом кадре.
Первоначальный `0x09` берёт **текущий** бит реле (`running_current`),
обновляемый всегда, даже если предыдущая посылка состояния не прошла.
ZT3L применяет принятые значения в ZCL-атрибуты и отвечает OK на каждый кадр.
System Mode (`0x0A`) и Running State (`0x09`) **не** шлются автоматически при
рукопожатии — только при реальном изменении (`0x0A` входит в дамп один раз;
`0x09` — в дампе и дополнительно при смене реле).

**Статус реализации.** CA51F2 — реализовано (`Link_Poll`, `h_net`,
`link_net_*` в `src/link_proto.c`; вызывается из главного цикла `main.c`).
ZT3L — реализовано: транспорт (`src/app_uart.c`) и протокол (`src/app_link.c`):
через **1 с** после старта шлёт Info Req (задержка `LINK_BOOT_DELAY_TICKS`
в `app_link.c` — CA51F2 теперь
отвечает на запросы уже во время своего boot-теста; ретраи 3×100 мс, далее
цикл 30 с до первого ответа), отвечает на Net-status Req (`0x1F`), принимает System Mode
(`0x0A`) и Running State (`0x09`) — применяет их в ZCL-атрибуты
(`g_zcl_thermostatAttrs.systemMode` / `.runningState`) и отвечает OK — и шлёт
спонтанный Net-status Rep при изменении сети (`zb_isDeviceJoinedNwk()`).
`App_Link_Poll()` вызывается из `app_task`, колбэк кадра — `App_Link_OnFrame`.
Время (`0x00`) — см. «Синхронизация времени»: ZT3L отвечает на TIME Req пустым OK,
опрашивает координатор и шлёт время обратно надёжной очередью `link_txq`.

## Синхронизация времени (Cmd `0x00` TIME)

Инициатор — **CA51F2** (не ZT3L). Формат: RAW(8) = `utc(4 BE)` + `local(4 BE)`,
unix-секунды.

| # | Отправитель | Кадр | Flags | DLC | Type |
|---|-------------|------|-------|-----|------|
| 1 | CA51F2 | TIME Req (`0x00`) | `0x02` (ACK) | 0 | — |
| 2 | ZT3L | TIME Rsp (`0x00`) | `0x01` (RSP) | 0 | — |
| 3 | ZT3L | ZCL Read (`Time` + `LocalTime`) координатору | — | — | — |
| 4 | ZT3L | TIME Cmd (`0x00`) | `0x06` (ACK\|CMD) | 8 | `11` RAW |
| 5 | CA51F2 | TIME Rsp | `0x01` (RSP) | 0 | — |

- **Шаг 1** — CA51F2 шлёт запрос: (1) при старте/рукопожатии, если сеть
  `CONNECTED` (переход `FREE → CONNECTED` или новый Info-запрос при уже
  подключённой сети), и (2) далее **раз в час**, пока сеть `CONNECTED`
  (`Link_Tick1s`, `LNK_TIME_PERIOD_SECS = 3600`, счётчик `link_time_age`).
  Запросы шлются только при `CONNECTED`.
- **Выход из сети**: RTC не трогаем — он продолжает идти на своём
  кварце с последним записанным временем; часовой ресинк останавливается
  (счётчик сбрасывается, возобновится после повторного `CONNECTED`).
- **Шаг 2** — только подтверждение приёма запроса (пустой OK), время не несёт.
- **Шаг 3** — ZT3L сам опрашивает координатор (ZCL Read `Time` + `LocalTime`).
- **Шаг 4** — по ответу координатора ZT3L шлёт время как **команду**, надёжно
  (ACK + 3 попытки/100 мс, далее раз в 30 с).
  ВАЖНО: ZCL `Time`/`LocalTime` — секунды от **2000-01-01**, а в кадре и в RTC —
  Unix-секунды (от 1970), поэтому ZT3L при отправке прибавляет
  `UNIX_TIME_CONST` (946684800). Без этого CA51F2 отбрасывает значение
  (`local < RTC_UNIX_MIN_TIME`) и часы остаются на `00:00`.
- **Шаг 5** — CA51F2 применяет `RTC_SetUnixTime(local)` (берёт локальную
  половину кадра, пишет её в RTC) и отвечает OK.
- Если ZT3L не в сети — отвечает `LNK_ST_NOT_READY` (без опроса); неверная DLC —
  `LNK_ST_BAD_LEN`.
- ZT3L больше не считает секунды сам и не опрашивает координатор периодически:
  опрос только по запросу CA51F2.

## Running state и режимы

**Running state** (Cmd `0x09`, тип bitmap16 — 2 байта BE, маска ZCL):

| Бит | Значение |
|-----|----------|
| 0 | `heat` (нагрев включён) |
| 1 | `cool` |
| 2 | `fan` |
| 3–15 | резерв = 0 |

Все биты = 0 → **idle**. Определяется MCU и репортится на ZR.

**System mode** (Cmd `0x0A`, enum u8 — значения ZCL `HVAC Thermostat`):

| Значение | Название |
|----------|----------|
| 0x00 | Off |
| 0x01 | Auto |
| 0x03 | Cooling |
| 0x04 | Heating (основной) |
| 0x05 | Emergency heating |
| 0x07 | Fan only |
| 0x08 | Dry |

В настоящем MCU простейший случай: on/off (heat/off). Термины cool/fan доступны
будут при расширении платы или в новых моделях.

**Sensor source** (Cmd `0x0C`, enum u8):

| Значение | Название |
|----------|----------|
| 0x00 | Internal (`IN`) |
| 0x01 | Outdoor (`OU`) |
| 0x02 | All (`AL`) |

**Prog op mode** (Cmd `0x0B`, тип bitmap8 — 1 байт; битмапа ZCL
`ProgrammingOperationMode`):

| Бит | Значение |
|-----|----------|
| 0 | `0` = ручной режим (setpoint mode), `1` = от недельного расписания |
| 1 | auto/recovery — **не поддерживается, отклоняется `LNK_ST_VALUE`** |
| 2 | `0` = Economy/EnergyStar выключен, `1` = **ЭКО включён** |

Принимаемые CA51F2 значения: **0x00, 0x01, 0x04, 0x05** (бит0 + бит2);
всё остальное (0x02/0x03/0x06/0x07 и выше, включая старое «Temporary»
0x02) → `LNK_ST_VALUE` (0x21). Значение передаётся **байтом целиком**
(без маскирования битов): хаб получает отказ и через `STATE_ALL`-ресинк
узнаёт фактический режим. Бит 2 (ЭКО): индикация — символ
Эко, при включении заданная температура управления снижается на фиксированные
3.0 °C (см. README, «Режим Эко»).

## Коды команд и данных

Назначены на основе сущностей ZR-проекта (40 DP_IDX) и кластеров ZCL
(Thermostat `0x0201`, Fan Control `0x0202`, Humidity `0x0405`).
Температуры (измеренные и заданные) — **i16 в сотых долях °C (масштаб `÷100`, как ZCL)**;
калибровка и гистерезис — в десятых (`÷10`, ZCL 0.1 °C); влажность — `u16 ×100`
(0..10000).
Если сущность отсутствует на конкретной плате — приёмник отвечает `Status != 0`
(не поддерживается), ZR не шлёт/не применяет её. Нет ошибки протокола.

**Реализовано на MCU (CA51F253L3, `lnk_table[]` в `src/link_proto.c`):**
`0x00` TIME — MCU сам шлёт TIME Req на переходе сети в `CONNECTED` и далее
ежечасно (`link_request_time`, счётчик в `Link_Tick1s`), применяет пришедший
TIME Cmd в RTC
(`h_time`). **На чужой TIME-Req CA51F2 НЕ отвечает** (мёртвый путь
«ответ текущим временем» — `RTC_GetUnixTime` + `lnk_put32` — удалён;
ZT3L Req не шлёт вообще, его единственная отправка TIME =
Cmd, а исключение `f->cmd != LNK_CMD_TIME` в правиле «не-OK → `STATE_ALL`»
(`app_link.c`) гарантирует отсутствие побочных эффектов; чужой Req получает
`BAD_FLAGS` — роль `REQ` убрана из таблицы). Оставшиеся роли `0x00`: Rep/Cmd;
`0x01` INFO — Req/Rep + ответ (роль CMD у CA не зарегистрирована); `0x1F`
NET_STATUS — MCU сам шлёт запрос (сразу после ответа на Info, через 100 мс,
3 попытки по 100 мс, далее цикл раз в 30 с до первого ответа — стейт-машина +
`Link_Poll()`), а как сервер только применяет чужой репорт (`h_net`). Репорты
температур `0x02` (`LNK_CMD_TEMP_LOCAL`, внутренний) и `0x03`
(`LNK_CMD_TEMP_OUTDOOR`, внешний): `Link_ReportTemps()` вызывается из `main`
раз в секунду, когда пир жив (`Link_PeerAlive()`, взводится по Info-запросу
ZT3L). Rep-кадры отправляются по политике ниже: первый accepted, изменение
accepted и keepalive для `0`.
Скалярные настройки, пришедшие из сети (см. «Запись настроек из сети»), MCU
принимает и применяет (`h_setting`: `0x07`/`0x0B`/`0x0C`/`0x0D`/`0x0E`/`0x0F`/
`0x10`/`0x11`/`0x17`/`0x1A`/`0x1B`) и `0x0A` SYSTEM_MODE (`h_sysmode`).
На все остальные Cmd после INFO-рукопожатия MCU отвечает `Status=0x10`
(`LNK_ST_UNSUPPORT`, не поддерживается); до INFO-рукопожатия (кроме своих
исключений Info/Net/`0xC0`/`0x2B`) — `0x32 NOT_READY`, а кадры без ACK
применяются молча, без ответа. Статус сети хранится в `link_net_status` и доступен через
`Link_NetStatus()`.

**Политика репортов беспроводного датчика климата (`0x04`/`0x06`, ZT3L → CA).**
Обработкой ZCL-репортов привязанного клиентского датчика
температуры/влажности (кластеры MS Temp Meas `0x0402` / MS RH Meas `0x0405`,
единая точка — `app_zclReportCmd()` в `TLSR8258/src/zcl_appCb.c`) занимается
ZT3L. Перед отправкой значение проверяется на корректность: температура
**−40.00…+125.00 °C** (−4000…12500 в единицах ZCL 0.01 °C), влажность
**0…100.00 %** (0…10000); границы вынесены в именованные константы
`WS_TEMP_MIN_C100` / `WS_TEMP_MAX_C100` / `WS_HUMID_MAX_C100` (единицы
ZCL ×100, как во всём проекте — правятся быстро). Невалидное значение (в т.ч. `0x8000` «measurement failed» и `0xFFFF`
«invalid» — они выпадают из диапазона сами) отбрасывается с логом
`ws t bad` / `ws h bad` (флаг `DEBUG_WS_EN` в `app_cfg.h`, по умолчанию ON)
и на CA не уходит. **Влажность перед отправкой округляется ZT3L до целого
процента и клампится 100 → 99**: на проводе
остаются прежние `u16 ×100` в диапазоне **0..9900**, CA рендерит значение
как есть, без какой-либо математики. Каждое **валидное** значение отправляется отдельным
надёжным кадром (`App_Link_SendWsTemp` / `App_Link_SendWsHumid`, `ACK|CMD`,
очередь `link_txq`) — **без порога изменения**: датчик шлёт не реже раза в
5 минут, каждый репорт пересылается как есть. Отправка идёт только при живом
пире (`App_Link_Ca51f2Alive()`), иначе значение молча отбрасывается (следующий
репорт придёт сам); телеметрия НЕ копится в pending-буфере настроек и не
запрашивает `STATE_ALL`.

Приём на стороне CA51F2 (этап 2): команды `0x04`/`0x06`
зарегистрированы в `lnk_table[]` (`{ ..., 2, I16/U16, REPORT|CMD, h_ws }`).
`h_ws` (`CA51F253L3/src/link_proto.c`) декодирует BE-значение и складывает в
RAM-переменные `ws_temp_c100` / `ws_humid_c100`, отвечая стандартным `OK`;
диапазоны на CA повторно НЕ проверяются (валидация — ответственность ZT3L).
Потребитель читает геттеры `Link_WsTemp()` / `Link_WsHumid()` /
`Link_WsFresh()` (объявлены в `CA51F253L3/include/link_proto.h`;
`Link_WsSeen()` и флаг `ws_seen` в коде больше нет).

Логика CA51F2 (этап 3): свежесть держит одно окно
`WS_FRESH_SECS = 300` с (`include/config.h` §7): счётчик `ws_age` тикает
раз в секунду (`Link_Tick1s`) и **обнуляется только кадром температуры**
(`ws_age = 0` в ветке `0x04`), причём `Link_Init` при загрузке ставит
`ws_age = WS_FRESH_SECS` (окно закрыто до первого TEMP-кадра: иначе один
кадр влажности открыл бы окно при начальном
`ws_temp = 0` → на экране «0», реле грело бы до первого кадра температуры).
`Link_WsFresh() = ws_age < WS_FRESH_SECS`. **Влажность своего счётчика не
имеет** — её валидность — то же окно. Пока WS свежая: `Relay_Update()`
получает `ws_c100/ws_active` и подменяет вход (`in := ws, src := IN`), т.е.
существующий одиночный гистерезис греет по беспроводному датчику вне
зависимости от IN/OU/AL, а `Temp_Draw()` первым делом показывает
WS-значение (правило «Er по AL» для WS не применяется). Протухла / не
приходила никогда → мгновенный возврат к настроенным датчикам, оба WS-значения
считаются недействительными. **Аварийная отсечка по перегреву — только по
проводным датчикам, WS в ней не участвует.**

Побочный эффект первого прогона: старый CA отвечал на
`0x04` `UNSUPPORT`, и общее правило ZT3L «не-OK от надёжного кадра → сразу
`STATE_ALL`» стоило полный дамп (≈20 кадров) на КАЖДЫЙ репорт датчика.
Исправлено: `LNK_CMD_TEMP_NET`/`LNK_CMD_HUMID_NET` исключены из этого
триггера в `app_link.c` (для телеметрии дамп всё равно ничего не чинит).

**Политика отсылки температур (0x02/0x03, `Link_ReportTemps`).** `Link_ReportTemps()`
вызывается раз в секунду, когда пир жив, и получает два независимых
**accepted-значения** из общего temperature pipeline независимо от выбранного
`SENSOR_SRC`. Репорты шлются через **зарезервированные слоты очереди** с
`ACK` (Cmd/DLC/Type/payload прежние), т.е. тоже подтверждаются, а shadow
обновляется только после matching `RSP OK`:
- первый accepted snapshot каждого датчика после рукопожатия (Info) отправляется
  первым;
- далее link отправляет значение, когда изменился соответствующий
  `accepted_c100`; pipeline уже применил правила первого значения, смены знака и
  порога `0.06 °C`, поэтому link больше не проверяет десятые доли и не применяет
  отдельный фильтр «десятая + 0.06»;
- если `accepted_valid == 0`, в кадр отправляется `0`; значение `0` повторяется
  хотя бы раз в **15 минут** (keepalive), потому что само по себе оно не
  изменяется. Правило одинаково для внутреннего и внешнего датчиков.

Совместимость: ZT3L принимает **и** старые отчёты без ACK, **и** новые с ACK.
Для отчёта без ACK дедуп-кэш инвалидируется перед применением и ответ не
отправляется; для отчёта с ACK значение применяется один раз, shadow
обновляется, и на `RSP=OK` отправляется `RSP OK` (SEQ копируется).
Символьный ноль-сентинел «датчика нет» в wire v1 сохранён: валидные `0.00 °C` и
«нет датчика» неразличимы, это осознанный компромисс v1.

Источник для управления/отображения CA51F2 выбирается по `SENSOR_SRC`
(0x0C): `IN` → внутренний, `OU` → внешний (обрыв → нагрев выключен,
фолбэка нет), `AL` → **оба датчика**: включение только когда оба
`≤ SP − deadBand`, выключение когда любой `≥ SP + deadBand` (AND-вкл /
OR-выкл); при отказе одного режим деградирует к одиночному закону по
выжившему, на экране `Er` (в `AL` вердикт `Er` — по валидности **обоих**
датчиков). Отображение: `IN` → значение внутреннего, `OU`/`AL` → значение
внешнего. ZT3L получает оба accepted-значения для 0x02/0x03.


**Локальные изменения настроек.** Когда настройку меняют на CA51F2 (стрелки —
заданная температура `0x07`; пункты меню — калибровки `0x0D`/`0x0E`, `deadBand` `0x0F`,
`sensosUsed` `0x0C`, лимиты `0x10`/`0x11`, яркости
`0x1A`/`0x1B`; лок-аккорд — `0x17`; редактор расписания — `0x20`..`0x26`), новое
значение шлётся в ZT3L **надёжно** (`ACK|CMD`, ретраи 3×100 мс / 30 с). ZT3L
применяет его в ZCL-атрибут и отвечает OK.

**Запись настроек из сети (ZT3L -> CA51F2).** Когда хост пишет ZCL-атрибут
(Write Attribute), ZT3L (стек уже записал значение в свой атрибут) пересылает
его в CA51F2 **командой** (`ACK|CMD`) через надёжную очередь `link_txq`
(`App_Link_SendSettingI16/U8`, ретраи 3×100 мс / 30 с). Соответствие атрибут ->
Cmd:

| ZCL-атрибут | ID | Cmd | Payload |
|-------------|----|-----|---------|
| `OccupiedHeatingSetpoint` | `0x0012` | `0x07` | i16 BE ×100 |
| `LocalTempCalibration` | `0x0010` | `0x0D` | i8 ×10 |
| `CustomExtTempCalibration` | `0xF00C` | `0x0E` | i8 ×10 |
| `MinSetpointDeadBand` | `0x0019` | `0x0F` | i8 ×10 |
| `ProgrammingOperationMode` | `0x0025` | `0x0B` | bitmap8 (байт целиком) |
| `SystemMode` | `0x001C` | `0x0A` | u8 |
| `MinHeatSetpointLimit` | `0x0015` | `0x10` | i16 BE ×100 |
| `MaxHeatSetpointLimit` | `0x0016` | `0x11` | i16 BE ×100 |
| `CustomSensorUsed` | `0xF000` | `0x0C` | u8 |
| `CustomLevel` (яркость день) | `0xF009` | `0x1A` | u8 |
| UI-cfg `KeypadLockout` | `0x0204`/`0x0001` | `0x17` | enum u8 (0..2) |

**Нормализация на ZT3L (clamp).** ZCL-стек записывает присланное значение в
атрибут **до** нашего колбэка, поэтому ZT3L перезаписывает атрибут зажатым
значением и в CA51F2 шлёт именно его (reject не используется):
заданная температура зажимается в `[minHeatSetpointLimit..maxHeatSetpointLimit]` (напр. 6000
-> 4500); `minHeatSetpointLimit` — в 500..1500, `maxHeatSetpointLimit` — в
2000..4500 (диапазоны непересекающиеся, `min <= max` выполняется само); калибровки — в −90..90 (x10); `deadBand` — в 5..25 (x10, 0.5..2.5 °C);
`ProgrammingOperationMode` передаётся **байтом целиком** (без маскирования —
CA51F2 сам отклоняет неподдерживаемые значения); `CustomSensorUsed` — 0..2;
`KeypadLockout` — 0..2 (tri-state); `CustomLevel` — 0..`maxLevelA`.
`MoveToLevel` зажимается в `maxLevelA/B` (0..8) и пишет `currentLevelA/B`.
Общие границы — `ABS_MIN/MAX_TEMP_CALIB` и `ABS_MIN/MAX_DEADBAND` в
`include_common/thermostat.h`.

CA51F2 проверяет длину/тип кадра на входе (`lnk_validate`), а значение — **на
входе в `settings`** (проверять там, где данные
попадают в `settings`): `h_setting` записывает поле и прогоняет **общий гейт
`settings_ranges_valid()`** по всему образу; при провале поле **откатывается**
к прежнему значению и ответ `LNK_ST_RANGE` (вне диапазона) / `LNK_ST_VALUE`
(недопустимый enum/биты) — значения не зажимаются. При реальном изменении образ
сохраняется через `settings_save()`, который **только персистит и не валидирует**
(свой гейт в `settings_save` откатывал ВЕСЬ живой образ и терял посторонние
несохранённые правки). Если активный A/B-банк нельзя надёжно записать или
прочитать, CA51F2 отвечает `0x41 LNK_ST_FLASH`, оставляет старый банк активным
и откатывает несохранённое изменение RAM.

**Лимиты независимы от заданной температуры/расписания.**
`0x10 minHeatSetpointLimit` принимается в диапазоне 500..1500 (5..15 °C),
`0x11 maxHeatSetpointLimit` — в 2000..4500 (20..45 °C), и **ни текущая
`occupiedHeatingSetpoint`, ни температуры расписания на это не влияют**: гейт
проверяет их только по абсолютным границам 500..4500. Раньше предлагаемый лимит
отклонялся с `LNK_ST_RANGE`, если оставлял заданную температуру или слот расписания вне
`[min..max]`; теперь отказ возможен, только если **само значение лимита** вне
своего диапазона (или образ невалиден по остальным полям). Лимиты в меню
(пункты 5/6) клампятся только к диапазону пункта: trial-запись через гейт в
`Menu_Step` удалена — она же давала баг «12 → 5» (откат в закоммиченное
значение при отказе гейта). ZT3L на не-OK ответе запрашивает
`LNK_CMD_STATE_ALL` и перезаписывает свои атрибуты.

Так как ZT3L уже зажимает значения, гейт на CA51F2 срабатывает в основном при
рассинхроне или при записи зависимых значений в неудобном порядке (хост должен
сначала расширить диапазон, потом сузить). Атрибуты без поля в `settings` CA51F2 (`frostProtect`,
`heatProtect`, `ecoMode`, эко-температуры, `sound`, `inversion`,
`screen_off_time`, `led_indicator`, `temperatureDisplayMode`,
`occupiedCoolingSetpoint`) остаются локальными для ZT3L и не пересылаются.
Если ответ CA51F2 `!= OK`, ZT3L запрашивает `LNK_CMD_STATE_ALL`, чтобы заново
выгрузить настройки и перезаписать свои атрибуты (пересинхрон). Исключения —
`TIME` и телеметрия `0x04`/`0x06` (для них дамп ничего не чинит — см. политику
WS-репортов выше).

Запрос дампа со стороны ZT3L ведёт единый хелпер `link_state_request()`
(`TLSR8258/src/app_link.c`): все три триггера — Net-status
запрос от CA51F2, дренаж pending-настроек и не-OK ответ — идут через него, и
`link_state_req_done` выставляется в `1` **только если `App_Uart_SendFrame`
принял кадр** (драйвер возвращает 0 при занятости — на стенде строка
`TLSR !!` — или в raw-режиме OTA). При отказе `link_pending_retry()`
(вызывается из `App_Link_Poll`, пока link поднят) повторяет запрос на каждом
поллинге, пока тот не уйдёт; раньше один занятый драйвер терял запрос
навсегда до следующего хендшейка, и хаб оставался с устаревшими атрибутами
без единой ошибки в логе.


**Яркость.** Кроме атрибута `CustomLevel` (`0xF009` -> `0x1A`, яркость дня),
яркость приходит и кластерной командой **Level Control `MoveToLevel`**
(`app_displayLevelCb` -> `app_displayMoveToLevelProcess` в `src/zcl_appCb.c`):
EP1 -> `0x1A` (день), EP2 -> `0x1B` (ночь). Значение `cmd->level` шлётся как
есть, диапазон **0..8** (`g_zcl_levelAttrs.maxLevelA/B = 8`, совпадает с
`LED_BRIGHTNESS_MAX` у CA51F2). Так доступна и **яркость ночи** (`0x1B`),
которой нет среди writable-атрибутов (Level Control `currentLevel` — read-only).

**Надёжная доставка состояний (0x09 Running State, 0x0A System Mode).**
CA51F2 шлёт их как **команду** (`Flags = ACK|CMD`) при изменении:
`0x0A` — `Type` enum, DLC=1; `0x09` — `Type` bitmap16, DLC=2 (2 байта BE).
- `0x0A` — при вкл/выкл термостата (`power_on` → `LNK_SYSMODE_OFF` / `HEAT`);
- `0x09` — при вкл/выкл реле (`LNK_RUN_HEAT` / `0`).
Любой ответ пира (RSP с тем же SEQ/Cmd) освобождает посылку; нет ответа 100 мс
→ повтор тем же SEQ, всего 3 попытки, далее раз в 30 с (та же политика, что у
Info/Net). Принятый от пира `0x0A` (Cmd) применяется: термостат включается, если
значение != `LNK_SYSMODE_OFF`, иначе выключается; ответ — OK.

**Очередь надёжных посылок.** `lnk_txq[]` в
`src/link_proto.c` (на ZT3L — `link_txq` в `src/app_link.c`):

- **Всего 6 слотов у CA51F2: 4 общих + 2 зарезервированных под
  температурные потоки** (`0x02`/`0x03`). Температуры не расходуют общие
  слоты, поэтому при полной очереди они всё равно уходят. У ZT3L
  (`link_txq` в `app_link.c`) `LINK_TXQ_N = 4` — **без** зарезервированных
  слотов (телеметрия WS там просто замещает тот же слот).
- `lnk_txq_post(cmd, flags, type, len, payload, delay)` возвращает `1` при
  принятии/слиянии и `0` при отсутствии места. **Вызывающий обязан обновлять
  свой state-sentinel только после успешного возврата** — иначе значение
  потеряется молча.
- Слот, уже вошедший в `WAIT_RSP`, при замене payload получает **новый SEQ**;
  поздний RSP старой пары `(SEQ, Cmd)` не освобождает замену.
- Слот хранит `session`; новая сессия (новый Info с новым SEQ) очищает peer-слоты
  и увеличивает номер сессии, поэтому поздний RSP старой сессии игнорируется.
- **RSP с ошибкой принимается независимо от DLC (обе
  стороны).** Полезная нагрузка ошибочного ответа игнорируется, но НЕ
  отвергает кадр: раньше `status != OK` с любым телом получал `BAD_LEN`,
  кадр отбрасывался до сопоставления слота → слот не освобождался никогда
  и команда ретраилась 3×100 мс / 30 с вечно, а реальный статус
  (`RANGE`/`BAD_TYPE`…) поглощался. Сегодня обе стороны посылают ошибки с
  пустым телом — ловушка была заряжена на будущее.
- **Полная очередь не теряет значения (CA51F2).** `Link_SendI16/U8()` переводят
  локальные настройки в ограниченный курсор-ретрай: значения читаются из уже
  сохранённого `settings` и переотправляются по одному, без повторной записи
  flash. Factory reset (`0x27`) имеет отдельный pending-флаг и не теряется.
  Дни расписания помечаются в `sched_send_mask` и повторяются по одному, пока
  пир жив; маска живёт **до самой доставки** — вход в редактор расписания её
  больше не затирает (день, записанный при мёртвом пире, теперь
  гарантированно доедет). **Пейсинг курсора:** `Link_RetryPending()`
  вызывается **раз в секунду** (секундный блок `main()`, рядом с
  `Link_Tick1s`), а не на каждой итерации главного цикла, и при отказе поста
  курсор **не откатывается в 0**, а держит текущий индекс, пока слот очереди
  не освободится. Без этих двух свойств цикл «пост → отказ → сброс в 0» при
  молчащем пире бесконечно переотправлял уже принятые настройки с новым SEQ
  (замена `WAIT_RSP`-слота) на rate главного цикла — десятки кадров в секунду
  вместо политики 3×100 мс / 30 с.
- **ZT3L при полной очереди** копит компактные pending-записи настроек и
  schedule-mask, переживает очистку очереди при handshake, повторяет их после
  handshake и **не отправляет** при `App_Ota_IsActive()`. `STATE_ALL`
  откладывается до опустошения pending.


### Расписание недели (0x20–0x26, по дням)

Неделя не влезает в один кадр (6 периодов × 4 Б × 7 дней = 168 Б), поэтому —
**один кадр = один день**: запись делается только на конкретный день
(чтение — через ZCL Get и push-дамп `STATE_ALL`).

| ID | День |
|----|------|
| `0x20` | Понедельник |
| `0x21` | Вторник |
| `0x22` | Среда |
| `0x23` | Четверг |
| `0x24` | Пятница |
| `0x25` | Суббота |
| `0x26` | Воскресенье |

Payload (RAW, 24 Б): 6 записей × 4 Б, big-endian:

| Поле | Тип | Описание |
|------|-----|----------|
| `transTime` | u16 | минуты от полуночи, 0..1439; `0xFFFF` = точка не используется |
| `heatTemp` | i16 ×100 | заданная температура, сотые °C |

Записи строго по возрастанию времени; неиспользуемые точки — в конце, со
временем `0xFFFF` **и температурой 0** (пустой слот не несёт никакого
значения). Роли: `Cmd/Data` (записать день), `Rsp`. Роль `Req`
(прочитать день) **удалена**: сквозной путь не работал (ZT3L
в RSP-ветке валидатора не имеет schedule-case и отвергал 24-байтовый ответ
CA как `BAD_LEN`, сам ZT3L Req никогда не шлёт), а чтение дня покрыто
ZCL Get (из зеркала ZT3L) и push-дампом `STATE_ALL`. Первый день недели —
понедельник (как ZCL attr `0x003B` StartOfWeek).

**Валидация и нормализация дня (правило CA-2).** Данные против
политики: на входе проверяются только **постоянные** границы, лимиты
`min/maxHeatSetpointLimit` применяются при ИСПОЛЬЗОВАНИИ заданной температуры и в данные
никогда не запекаются — и это верно для **обоих** режимов: ручная заданная
температура (MANUAL) тоже проходит через use-time кламп в `Sched_ActiveSetpoint()`
(фикс M4): активное значение зажимается в `[min..max]` перед
подачей в реле, в `settings` остаётся записанное. Раньше manual и fallback
до первого перехода возвращали исходную заданную температуру, и рассинхрон «заданная температура > max»
(пункт меню «max» или две хаб-записи `0x07`→`0x11`) выводил аварийную
отсечку `max + 2.5 + 1.0` ниже нормальной точки выключения
`SP + deadBand`. Что проверяется на входе конкретного дня:
- **ZT3L** (`App_Thermostat_SetWeeklySchedule`): `transTime`, отличный от
  `0xFFFF`, зажимается к **1439** (23:59; переход никогда не отбрасывается);
  температура зажимается к **ABS** (5.00..45.00 °C); слот с `0xFFFF`
  (полученный или хвостовой) сохраняется с температурой **0** — протухшие
  значения не пишутся ни при каких условиях. **`numOfTransForSequence == 0`
  отклоняется `ZCL_STA_INVALID_FIELD` до каких-либо записей**:
  нулевой счётчик не несёт данных, а применение стёрло бы каждый выбранный
  день хвостовым циклом и ответило бы SUCCESS.
- **ZT3L** (`Get Weekly Schedule`): `numOfTransForSequence` = число
  **реальных** переходов (пустые `0xFFFF` компактизируются и наружу не
  отдаются — хаб рисует `0xFFFF` как `1092:15`); полностью пустой день
  отвечает одной записью.
- **CA51F2** (`h_sched`): пустые слоты (`0xFFFF`) пропускаются; непустые
  проверяются по времени `≤ 1439` и **ABS** — отсылка к лимитам из
  ingress **удалена** (раньше слот вне лимитов ронял целый день в
  `LNK_ST_RANGE`); `RSP/Rep` — без изменений.

Полный кадр дня (запись из CA51F2 в ZT3L): `AA 55 SEQ 06 00 20 18 0B
<24 данных> CRC` = **33 байта** (`Flags=0x06` = ACK|CMD, `Status=00`,
`Cmd=0x20` = день, `DLC=0x18` = 24, `Type=0x0B` = RAW).

**ZCL-команды расписания на ZT3L.** Логика вынесена в новый
`src/app_thermostat.c`/`app_thermostat.h`; `app_thermostatCb` (`src/zcl_appCb.c`)
только диспетчер. `Set Weekly Schedule` (0x01) раскладывает переходы по дням в
`g_zcl_scheduleData` и пересылает каждый изменённый день в CA51F2
(`0x20..0x26`, `ACK|CMD`, RAW(24), надёжная очередь `App_Link_SendSchedule()`);
`Get Weekly Schedule` (0x02) отвечает по одному кадру на запрошенный день
и отдаёт **только реальные переходы**
(`numOfTransForSequence` = компактный счётчик, см. «Валидация и
нормализация дня» выше).
`Setpoint Raise/Lower` (0x00) оставлен закомментированным.

### Действия (CMD-роль, без данных — для чистых команд)

| ID | Действие | Тип | Роль |
|----|----------|-----|------|
| `0x27` | Сброс настроек (factory reset) | — | CMD |
| `0x28` | Запрос всего состояния | — | CMD |
| `0x2A` | Уведомление о рестарте CA51F2 (boot notice) | — | CMD |
| `0x2B` | Alive-пинг (liveness probe) | — | REQ |

Роль `CMD` = `Flags = RSP=0, ACK=1, CMD=1`. Приёмник отвечает
`Status=0` (выполнено) или `Status != 0` (не поддерживается / ошибка).

**`0x2B` Alive-пинг — watchdog UART на ZT3L.** ZT3L шлёт пустой
Req (`Flags = ACK`, `DLC = 0`, **свой свежий SEQ**, минуя надёжную очередь)
раз в `LINK_ALIVE_PERIOD_TICKS` = 60 с и ждёт любой входящий кадр от CA51F2.
Правила:

- **любой валидный кадр** (ответ на пинг, температура, что угодно) немедленно
  обнуляет счётчик ударов — засчитывается ещё ДО валидации, поэтому даже
  `UNSUPPORT` от старого CA51F2, не знающего `0x2B`, означает «линия жива»;
- окно тишины (60 с без единого входящего кадра) += 1 удар; **3 удара подряд**
  → ZT3L переинициализирует свой UART-подсистему
  (`App_Uart_Reinit`: ожидание TX-idle ≤8 мс, сброс кольца/парсера,
  `drv_uart_pin_set` + `drv_uart_init` = тот же `uart_reset()` + re-arm DMA,
  что делает чип-reset) и обнуляет счётчик; событие логируется строкой
  `uart reinit` (флаг `DEBUG_ALIVE_EN`);
- **во время OTA пинг/подсчёт/реинит не выполняются** (raw-канал нельзя
  ронять): вся логика сидит под гейтом `!App_Ota_IsActive()`;
- пинг сознательно НЕ идёт через надёжную очередь: его error-ответ не может
  триггерить ресинк `STATE_ALL`, слот очереди не занят;
- CA51F2 отвечает `OK` generic-путём, **даже до хендшейка** (команда
  добавлена в список pre-handshake исключений вместе с Info/Net/`0xC0`).

Мотивация: у TLSR «умирал» приём (в логе одни
`TLSR ->`, ни одного `CA51 ->`/`CA51 <!`), лечилось только ручным reset;
первопричина живёт ниже парсера (неочищенный аппаратный флаг ошибки RX), и
watchdog восстанавливает тракт без вмешательства пользователя.

**`0x27` Factory reset — вход в сеть.** CA51F2 шлёт его при **OFF + удержание
вниз ≥ 2 с** (событие начала мигания знака «сеть», `Net_Flash_Start`), надёжно
(`ACK|CMD`, ретраи). ZT3L отвечает OK и затем выполняет factory-new reset
(выход из сети + сброс NV, `zb_factoryReset()` с задержкой ~0.5 с, чтобы ответ
успел уйти). После этого ZT3L заново проходит рукопожатие (Info).

## OTA CA51F2 через Zigbee (реализовано)

Полный поток: хаб → Zigbee-OTA → TLSR8258 (клиент) → UART1 → CA51F2. TLSR8258
ретранслирует образ в дисплейный MCU. Дизайн: `doc_local/ota_ca51f2_design.md`.

### Распознавание образа (TLSR)

Образ CA51F2 упаковывается `tools/make_ca51f2_ota.py` в формате
`include_common/ca51f2_ota.h`: 32-байтовая шапка (magic `"CA51F2"` по смещению 0,
`5D 02` по 6, `4B` по 8, version u16 LE по 9, crc32 u32 LE по 12, bin_size u32 LE
по 24), затем сырой bin и 4-байтовый трейлер CRC-32. `bin_size` обязан быть
`128..0x7E00`; общий предел `LNK_OTA_PROGRAM_MAX` проверяют упаковщик, TLSR,
CA51F2 и XRAM-флешер. Упаковщик отклоняет oversized input до создания output.
Приёмник ZCL-OTA кладёт payload в flash TLSR по `0x77000`. На `OTA_EVT_COMPLETE` TLSR:
- нет magic `"CA51F2"` → штатный `ota_mcuReboot()`;
- magic есть → проверка CRC-32 образа, затем сравнение version из шапки с
  `ver_app` CA51F2 из Info. **Равны → пропуск** (цикл не повторяется).
- Различны и CA51F2 на связи → передача по UART1.

**Версия принимается только из валидного Info.** `ver_app` CA51F2
берётся из ответа Info лишь при `Status = OK` **и** полной длине version-поля
(проверка на ZT3L в `app_link.c`, на CA51F2 — в `lnk_validate()`). Info с
ошибкой или обрезанной длиной версии не запускает передачу: иначе «старая» или
нулевая версия заставила бы TLSR вечно пересылать один и тот же образ.

Слот `0x77000` стирается и `SYSTEM_RESET()` выполняется **только** после того,
как CA51F2 после перезагрузки **покажет новую версию в Info**: состояния
`ST_WAIT_DONE` → `ST_WAIT_BOOT`, возврат в кадровый режим
(`App_Uart_SetRaw(0)`), обычное Info-рукопожатие, и лишь при
`App_Link_Ca51f2Ver() == ota_img_ver` — стирание слота и сброс.

### Управляющая команда

- `0xC0 OTA_START` (TLSR → CA51F2), **`ACK|CMD`**, `RAW(6)`: `bin_size` u32 BE +
  `version` u16 BE. Валидация на CA51F2: только `ACK|CMD`, только RAW, `DLC = 6`,
  `bin_size` в `128..LNK_OTA_PROGRAM_MAX` (`0x7E00`), `version != 0`. Ответ RSP:
  `0x00 OK` / `0x31 BUSY` / `0x20 RANGE` / `0x13 BAD_FLAGS` / `0x11 BAD_LEN` /
  `0x12 BAD_TYPE`.
- **Идемпотентность START.** CA51F2 запоминает принятую тройку
  `(SEQ, size, version)` и её ответ. Точная ретрансмиссия возвращает cached `OK`
  **без** повторного обновления состояния хендоффа; **другой** OTA_START при
  pending возвращает `BUSY`. Это позволяет TLSR безопасно повторять START при
  потере RSP.
- **`BUSY` — retryable только для уже принятого tuple.** TLSR повторяет тот же
  SEQ только если BUSY относится к его собственному принятому START; `BUSY` от
  чужого tuple переводит OTA в терминальный `ST_ERROR` (возврат в кадровый
  режим).
- При OK CA51F2 принудительно выключает реле и передаёт управление XRAM-флешеру.
  **Pending-состояние OTA (`Ota_IsPending()`) глушит весь кадровый обмен:**
  `Link_Poll()` не вызывается, `Link_Tick1s()`/`Link_ReportTemps()`/
  `Link_UpdateStates()` и локальные link-send пути ничего не отправляют, а
  `Link_OnFrame()` отклоняет не-OTA **команды** (`BUSY` на ACK-запросы;
  отчёты без ACK отбрасываются молча), тогда как **RSP-кадры обслуживаются
  раньше OTA-гейта** — они освобождают слоты очереди и подтверждают уже
  отправленное. `Link_BootNotify()` (`0x2A`) при pending не
  отправляется. Условие `enable` реле содержит `!Ota_IsPending()`.
- TLSR при `App_Ota_IsActive()` подавляет надёжную очередь и net-status traffic,
  но **продолжает Info-рукопожатие** — оно нужно для проверки версии после OTA.
  Non-OTA входящие кадры в OTA-окнах (рамочные окна: до входа в raw и
  `ST_WAIT_BOOT`; в сыром режиме парсер выключен и фильтр недостижим)
  теперь отвечают **`BUSY`**, а не глотаются молча:
  исключения `0xC0`/Info/boot обрабатываются как раньше (это пути
  завершения самой OTA), RSP и отчёты без ACK BUSY не получают
  (`app_link_send_error` молчит на них). CA в свою очередь на `RSP BUSY`
  **не убивает слот очереди**, а сразу переводит сообщение в медленный
  30-с режим (`tries = LNK_TXQ_TRIES`) — значение не теряется и быстрые
  ретраи прекращаются. `App_Uart_SetRaw(1)` ровно один раз переводит
  владение UART и сбрасывает кольцо кадрового приёма;
  `App_Uart_Poll()` продолжает обслуживать raw-приём.

### Сырой протокол данных (кадры выключены)

После OK обе стороны выходят из кадрового режима (TLSR —
`App_Uart_SetRaw(1)`; CA51F2 исполняет флешер из XRAM, опрос UART1 без
прерываний).

- **Блок** (TLSR → флешер): `SYNC 0x5A | OFF_HI | OFF_LO | LEN | DATA[LEN] | CRC8`.
  `OFF` — абсолютный адрес в PROGRAM-area CA51F2 (`0..0x7DFF`), выровнен на 128;
  `OFF+LEN <= bin_size <= 0x7E00` (последний блок может быть короче); `LEN` 1..128;
  `CRC8` — CRC-8/MAXIM
  (отраж. `0x8C`) по `OFF_HI..DATA`.
- **Ответ флешера — токенизированный, 3 байта:**
  `ACK 0x06 | OFF_HI | OFF_LO` или `NAK 0x15 | OFF_HI | OFF_LO`
  (`LNK_OTA_RSP_LEN = 3`). Одно-байтовые ACK/NAK больше не используются: без
  offset поздний ответ за предыдущий блок мог продвинуть не тот блок. TLSR
  сверяет offset ответа с ожидаемым и отбрасывает «протухшие» ACK/NAK.
- **Правила приёма блока во флешере** (`expected_off`, стартует с 0):
  - CRC не сошёлся / `LEN == 0` / `LEN > 128` → `NAK`, состояние не меняется;
  - `off > expected_off`, `off % 128 != 0`, `off+len > total` или
    `off+len > 0x7E00` → `NAK`, ничего не стирается и не пишется;
  - `off < expected_off` (**дубликат**) → `ACK` **без** erase/write и без роста
    `expected_off`;
  - иначе `write_sector_checked(off, len)`: erase program-сектора `FSCMD=7`,
    запись `FSCMD=6`, `LOCK=0x29`/`0xAA`, затем **обратное чтение** всего блока
    (`FSCMD=5`) и побайтовое сравнение. Только после успешного readback
    `expected_off += len` и уходит `ACK`; при неуспехе erase/записи/чтения —
    `NAK` **без** продвижения;
  - data-область `0x7E00..0x7FFF` не затрагивается.
- **Служебные**: `READY 0xA5` (флешер готов, после входа и после `RESTART`),
  `RESTART 0xA6` (TLSR → флешер: сброс `expected_off` на 0 и повторный `READY`),
  `DONE 0xA8` (флешер → TLSR: образ записан целиком).
- **`DONE` = commit.** Флешер шлёт `DONE` **только** при
  `expected_off == total` и **повторяет** его во время success-hold ~3 с, чтобы
  потерянный байт был восстановим. `DONE` не означает завершения всей
  транзакции: TLSR после него всё равно ждёт проверенного boot.
- После записи всего образа REMAP остаётся включённым и
  выполняется `LJMP 0x0000`: очистка REMAP до следующей выборки команды разорвала
  бы исполнение флешера из XRAM.

### Повторы, таймауты и границы

- **Байтовый таймаут флешера.** Каждый байт (SYNC, OFF, LEN, DATA,
  CRC) читается через `rx_byte_timed()` с конечным внутренним счётчиком
  `FLASHER_RX_TIMEOUT_INNER = 0xFFFF` (`flasher.c`; фактическая длительность
  не измерена — см. «Замечания», PENDING). Таймаут на любом байте: текущий
  кадр бросается, на экране `Er`, флешер возвращается к поиску `SYNC` (не
  зависает). Поллинг `FSCMD` erase/write тоже ограничен конечным счётчиком; на
  исходе — `NAK` без продвижения.
- **Контракт неравенства таймаутов.** `LNK_OTA_FLASHER_BYTE_TIMEOUT_MS (100)
  < LNK_OTA_TLSR_ACK_TIMEOUT_MS (1000)` проверяется `#if` на этапе
  компиляции, так что заявленный байтовый таймаут короче ACK-таймаута TLSR.
  Внимание: реальный цикл `rx_byte_timed()` завязан на
  `FLASHER_RX_TIMEOUT_INNER` (0xFFFF) и на `LNK_OTA_FLASHER_BYTE_TIMEOUT_MS`
  не ссылается — соответствие 100 мс нужно подтвердить на стенде
  (см. «Замечания», PENDING).
- `OTA_START`: нет RSP → повтор **того же SEQ** (3 попытки). После исчерпания
  попыток TLSR **оптимистично** входит в raw-режим и ждёт `READY` (потерянный
  RSP не должна оставлять CA51F2 уже работающим флешером). Если `READY` не
  пришёл за ограниченное время — возврат в кадровый режим/ошибка. Это recovery
  без бутлоадера; bench-калибровка длительности — **pending**.
- Ожидание `READY`/блока — ограниченное число попыток с `RESTART` между ними.
- Блок: `NAK` или нет matching ACK за 1000 мс → повтор блока (ограниченное
  число попыток); исчерпание → `RESTART` и вся передача заново, затем терминальная
  ошибка. **Слот `0x77000` не стирается, TLSR не перезагружается**, образ
  сохраняется для следующего OTA-цикла.
- **Восстановление при пропаже питания — только ISP.** Сырых `LNK_OTA_ABORT`
  (`0xA7`) в протоколе нет и он не отправляется: после первой erase-записи
  безопасного возврата в приложение не существует (нет бутлоадера), поэтому
  состояние «флешер живёт в XRAM» после потери питания восстанавливается только
  перепрошивкой по ISP (`make flash-cachip`). До хендоффа (до первого erase)
  неудачный START полностью восстановим в кадровом режиме.

### Индикация на дисплее CA51F2

- **Старт обновления:** приложение перед хендоффом рисует «UP» на больших
  цифрах и включает дисплей/подсветку на максимум. REG-COM драйвер сканирует
  `LXDAT` аппаратно, поэтому картинка держится всё время прошивки (CPU не нужен).
- **Успех:** флешер после записи всего образа показывает «AL» ~3 с, затем
  прыгает в новую прошивку (дальше её boot-тест).
- **Отказ** (TLSR перестал слать блоки, таймаут ожидания блока ~20 с): флешер
  показывает «Er» и остаётся ждать (без сброса и **без** возврата в
  приложение — после хендоффа его больше не существует); восстановление —
  перепрошивка по ISP. Битые блоки — временные (повтор), глобальный CRC
  проверяет TLSR до передачи.

### Замечания

- **Ограниченное ожидание vs. измерительная калибровка.** Все таймауты
  флешера/передачи объявлены числами, но `FLASHER_RX_TIMEOUT_INNER = 0xFFFF` —
  это **контракт**, откалиброванный по уже существующему 3-секундному hold-петле,
  а не измеренная на кремнии величина. Фактическую длительность нужно подтвердить
  осциллографом на стенде; до этого заявления «таймаут срабатывает корректно»
  делать нельзя. **PENDING.**

- На CA51F2 нет бутлоадера/разделения app: применяется streaming XRAM-флешер
  (сборка `CA51F253L3/src/flasher/flasher.c`, блоб встроен в приложение).
  Риск «кирпича» — только при пропадании питания в момент записи (устройство
  питается от сети); состояние лечится только ISP, повторная OTA возможна лишь
  до первого erase.
- `bin_size` CA51F2 публикует флешеру в XRAM `0x07F0` (**u16 LE**;
  приложение и флешер всегда собираются вместе, расхождения версий нет; сам
  `OTA_START` на проводе остаётся u32 BE).
- Резерв команд: `0xC1..0xDF` свободны; `LNK_OTA_ABORT 0xA7` зарезервирован и
  намеренно не используется.
